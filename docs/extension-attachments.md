# VS Code workspace image insertion design

Milestone 2.2 defines the workflow for a later implementation. Folio's VS Code adapter currently renders supported workspace images through `extension/src/resources.ts`. Its upload operation remains disabled. Standalone image import uses the browser adapter and stores an embedded image with the document.

## Selection and destination

1. Add an **Image from file** action in the VS Code editor. Use a webview file input for the desktop user's local file, including when the workspace extension host runs on another machine. Read one file, cap it at 5 MiB before allocating or transferring it, and send bounded bytes plus the display filename through the existing connection envelope. A browser MIME type is an early filter. The host validates the byte count, extension, and raster signature using the same formats as workspace preview. Reuse the existing image dialog for alt text and insertion. Start with this picker flow before considering drag and drop or paste. [VS Code Remote webviews](https://code.visualstudio.com/api/advanced-topics/remote-extensions#using-the-webview-api)
2. The host derives the document and workspace folder from the active custom editor session. Require a saved file in a writable, supported workspace folder. A called operation is bound to that document URI, containing folder URI, and connection. Offer the document-relative `assets/` directory by default. An optional resource-scoped `folio.attachments.directory` setting can specify a path relative to the containing workspace folder. Preview the target before writing. Validate settings from the workspace using the same rules as user-supplied paths, and check provider writability again when starting a write. A provider-wide writable result can coexist with read-only directories or a read-only Markdown document. Handle per-file metadata and actual write or permission errors. [VS Code FileSystem API](https://code.visualstudio.com/api/references/vscode-api#FileSystem)
3. Sanitize the basename for portability across Windows, macOS, and Linux. Strip path components, normalize Unicode to NFC, remove controls and Windows-reserved characters, and trim trailing dots and spaces. Use `image` for an empty stem or a Windows device name. Limit the stem to 100 UTF-8 bytes on a code point boundary and derive the lowercase extension from the validated format. Keep the original display stem for alt text. On collision, try `name-2.ext` through `name-100.ext`. Use a no-overwrite filesystem operation for the final name even when a preceding stat found it free. Treat canonically equivalent or case-folded existing filenames in that directory as collisions for checkout portability.
4. Calculate the link from the document's parent URI to the finalized asset URI using POSIX URI path segments. Verify that both URIs are in the same workspace folder, scheme, and authority. Percent-encode each filename segment once, including spaces, `#`, `%`, and parentheses. Keep `/` between segments and emit `./assets/name.png` or bounded `../` steps. Test the emitted reference through the existing resolver before returning it to the webview. Save only the relative reference in Markdown.

## Filesystem boundary

Put validation and publication in a host service next to `extension/src/resources.ts`. Share the raster signature checks and lexical containment rules with resource reads where their semantics match. Use URI segments, `Uri.joinPath`, and `workspace.fs` for provider-backed resources. Disallow absolute and parent segments in the configured asset directory. Walk from the selected root and reject symlinks, non-directories, encoded separators, controls, device names, and root or authority changes. Recheck the nearest existing parent before directory creation, then verify every component. For a `file` URI available to the extension host, also check canonical containment and use an exclusive, no-follow stage creation primitive where available. Revalidate before publication and after reading the final bytes. [VS Code virtual workspace guidance](https://code.visualstudio.com/api/extension-guides/virtual-workspaces)

The common provider API has no atomic no-follow walk, `writeFile` can replace existing bytes, and `rename` semantics depend on the provider. Before enabling a provider for insertion, establish that it reports link metadata accurately and supports an exclusive staging create plus a same-directory no-overwrite publication under concurrent writes. Evaluate `WorkspaceEdit.createFile` with `contents` and overwrite disabled for the staging write, including whether it leaves an Undo entry for a staging path after publication. Use a provider-supported staging primitive if that entry interferes with native history. For a provider that cannot satisfy these requirements, surface an unsupported destination before creating files. Local canonical checks and subsequent validation still leave a filesystem race when the provider has no operation that can enforce containment through the write. Document the guarantee for each supported provider and leave it disabled where that gap cannot be accepted. [VS Code WorkspaceEdit API](https://code.visualstudio.com/api/references/vscode-api#WorkspaceEdit)

Existing image references continue through the current document parser, serializer, and preview service. An ordinary edit leaves authored relative paths, reference syntax, and image metadata intact. Folio sends validated preview bytes into the existing CSP and keeps workspace directories out of `localResourceRoots`.

## Publication and recovery

1. Wait for the active view's existing edits to settle, then capture the insertion position and committed revision. If the selection or committed revision changes while the request runs, ask for a new insertion position before changing Markdown. Bind prepare, publish, and status replies to the initiating connection and a host-issued operation ID. An operation ID makes status requests idempotent. Keep an operation record in VS Code workspace storage separately from the Markdown draft journals.
2. Before filesystem changes, persist the operation ID, document and root URIs, staging URI, candidate final URI, byte length, digest, and stage. Use a uniquely named staging file in the destination directory. Persist a new intended final URI before each collision retry. Verify the staged bytes and publish under the chosen name with overwrite disabled. Verify the final regular file and digest, record publication, and then return the relative reference. Provider failures can be reported after a write took effect, so classify the result by checking both paths after the connection returns.
3. Insert the link through the existing shared edit path. The editor journal and host backup immediately checkpoint the new draft. The normal native acknowledgement still verifies the exact proposal against `TextDocument`. Save, Undo, and Redo follow VS Code's Markdown history. The binary asset may be shared or become referenced later, so Undo removes the Markdown reference and leaves the file. A status record can report a published asset independently of whether the link was acknowledged.
4. On interruption, inspect the operation record and revalidate workspace identity before reading either path. If neither file exists, prompt for reselection when the originating bytes are gone. If an owned stage still exists, verify it before offering retry or cleanup. If the final file exists with matching bytes, offer its relative path for explicit insertion or copy. Ambiguous ownership or changed bytes require manual review. Recovery never inserts text automatically after a restart. A rename, deletion, changed root, or conflict requires a fresh insertion decision. Only remove a staging file after verifying it still belongs to the operation. Never automatically remove a published or ambiguous file. Markdown recovery remains available independent of the operation record.

## Implementation and acceptance tests

| Step | Code ownership | Acceptance coverage |
| --- | --- | --- |
| Validate paths and bytes | Host resource service and pure helpers near `src/host/vscode/resourcePath.ts` | Relative paths round-trip from nested documents and filenames with spaces, Unicode, `%`, `#`, and parentheses. Reject traversal, encoded separators, device names, cross-root paths, different authorities, symlink components, false MIME labels, SVG, and oversized or truncated inputs. Existing images still preview and retain their source bytes after ordinary editing. |
| Stage and publish | New host attachment service and workspace-scoped operation records | Inject create, partial write, permission, quota, and rename failures. Assert duplicate requests are idempotent, parallel inserts preserve both files, and a pre-existing file or case-only collision is never overwritten. Verify a read-only folder leaves the Markdown buffer and disk unchanged. |
| Wire insertion to the editor | `src/host/vscode/protocol.ts`, `extension/src/extension.ts`, VS Code host adapter, and shared image dialog | Assert the path reaches Markdown only after publication, stays relative after cloning the workspace, and participates in native Undo, Redo, and Save. Exercise Source, Visual, and Split, two Folio views, concurrent native edits, wrong connection or revision, delayed acknowledgement, and UTF-8 BOM/CRLF. Standalone local image import and IndexedDB tests still pass. |
| Recover interruptions | Host operation status and existing draft recovery UI | Interrupt before staging, during write, after promotion, and after Markdown applies but before acknowledgement. Restart the host, reconnect, replace or rename the document, and check that assets are neither duplicated nor deleted by recovery. Verify exact pending Markdown and workspace isolation. |
| Qualify supported environments | Desktop VS Code integration and the deployment matrix | Run on native Windows, macOS, and Linux and at least one real Remote workspace. Pick an image from the client, write it into the remote root, verify bytes and `TextDocument` state, disconnect and reconnect, and check that a second root cannot receive the asset. Synthetic provider tests cover fault injection and do not qualify the real transport. |
