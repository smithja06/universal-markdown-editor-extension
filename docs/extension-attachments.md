# VS Code workspace image insertion design

Folio's VS Code adapter renders supported workspace images through `extension/src/resources.ts`. Automatic attachment writes are disabled on every backend. Standalone image import uses the browser adapter and stores an embedded image with the document.

## Milestone 2.4 architecture decision

Keep image insertion in VS Code reference-only. The user places an image inside the workspace, then adds a document-relative reference using **Insert content → Image or image caption** in Visual or the Visual pane of Split. In Source or the Source pane of Split, type or paste the Markdown reference directly. For example, for `docs/readme.md` and `media/café #%(draft).png` in the same workspace, use `../media/caf%C3%A9%20%23%25%28draft%29.png` in the image dialog, or `![Workspace illustration](../media/caf%C3%A9%20%23%25%28draft%29.png)` in Source. Encode reserved characters in each segment once. Keeping the image and document in the same relative layout makes the link portable.

The shared insert dialog applies by button click or Enter without native form submission, which the VS Code webview sandbox blocks. Folio reads the image for preview and edits the Markdown through the existing editor path and native `TextDocument` history. VS Code Save persists the reference, and Undo/Redo change the reference while the user's asset stays in place. Moving or replacing the asset can change or break its preview. The existing resolver's read-side race limits still apply.

### Threat model for automatic writes

The filesystem threat model assumes a trusted operating system and extension runtime. Other processes may have ordinary write access to workspace entries or their ancestors, including processes running under the same user account.

| Condition | Required behavior before enabling a backend |
| --- | --- |
| Accidental collisions and ordinary filesystem errors | Stage exclusively, publish atomically without replacing an existing entry, and handle denied access, read-only paths, quota, missing directories, and unsupported primitives. Keep Markdown unchanged until publication is verified. |
| Concurrent non-malicious changes | Independent tools and other Folio views can create names, rename directories, or replace entries. Stay within the bound workspace, preserve existing bytes, enforce the documented NFC and case-equivalence rule at publication, and refuse stale Markdown insertion positions. |
| Interrupted writes and extension-host crashes | Record intent before relevant changes and distinguish partial stages, published assets, and ambiguous outcomes. Only retry or delete where the backend can demonstrate ownership through the operation. Leave ambiguous entries for manual review and never replay an insertion position after restart. |
| Malicious concurrent filesystem modification | Keep the same containment, no-overwrite, and ownership guarantees when a process can mutate ancestors, reparse points, or names during the operation. Disable writes unless the backend can enforce that boundary. VS Code Workspace Trust and folder naming alone do not restrict another process's filesystem access. |

### Options evaluated

| Option | Assessment |
| --- | --- |
| **A. Handle-anchored NTFS backend** | The x64 Windows probe establishes useful live-handle primitives, but it starts from an absolute path and leaves the trusted-volume-to-workspace chain and in-place reparse mutation unqualified. A production backend would have to anchor and verify the whole chain, qualify sharing and mutation behavior, and preserve stage ownership for any restart action. Closing handles ends the live proof. File IDs and digests help classify outcomes but do not grant ownership of a new entry. NTFS also allows the tested NFC and NFD names to coexist under anchored publication. Shipping and maintaining a native helper across Windows architectures, filesystems, and other hosts would still leave those questions to solve. [Microsoft `NtCreateFile` reference](https://learn.microsoft.com/windows/win32/api/winternl/nf-winternl-ntcreatefile) |
| **B. Dedicated destination or enforced boundary** | A conventional `assets/` directory, a user-selected directory, and an application lock leave independent writers with the same access. A separately secured service identity and directory or an equivalent provider-enforced boundary could restrict who can create, replace, or reparse entries. It would have to protect ancestors as well as the destination, keep the asset inside the workspace for portable links, mediate every writer in its publication namespace, and define restart ownership. Windows ACLs are enforced against a process's access token, so a directory writable by the extension's ordinary user token gives no general isolation from other processes using that token. A dedicated identity or provider adds provisioning, permissions, portability, and support costs that ordinary checkouts do not justify. [Microsoft file access rights](https://learn.microsoft.com/windows/win32/fileio/file-security-and-access-rights) |
| **C. Reference to a user-placed image** | **Selected.** The existing dialog and editor can store a portable relative reference using the current preview boundary. No Folio asset write means no staging or publication race, asset journal, restart cleanup, or new native dependency. It works through the existing preview APIs, with Windows local and synthetic-provider preview coverage and platform-specific coverage limits below. The user is responsible for placing and retaining the image. |

An opaque ASCII basename derived from an operation ID could reduce accidental collisions and keep the original name in alt text. It is a candidate for a future backend only if the generated alphabet and volume semantics make the chosen portable equivalence contract enforceable under independent writers, or an enforced boundary prevents such writers altogether. Randomness, NFC normalization, or enumeration alone cannot close the publication race. Even a proven naming strategy would leave ancestor containment and restart ownership to solve.

## Milestone 2.5 reference-only picker

**Browse workspace images** opens the VS Code file dialog at the workspace folder containing the initiating Markdown URI. Visual and Split use the existing image dialog, and Source opens it from **Insert image**. A valid choice fills **Image URL** with a document-relative reference. Users can edit alt text before inserting, enter a reference manually, or cancel without editing Markdown. The file dialog lists the current directory on demand. Folio checks the single returned URI and rejects files from other roots even in the same window. [VS Code file dialog API](https://code.visualstudio.com/api/references/vscode-api#window.showOpenDialog)

The browse action requires a local Windows extension host, a drive-letter `file:` workspace with an empty URI authority, and a fixed NTFS volume. Folio queries the initiating drive through Windows PowerShell and CIM when the user browses. It rejects linked ancestors and a root that resolves to a different path. The dialog reports known read-only Markdown, a missing workspace folder, or an unsupported provider. A read-only image can still be referenced by a writable document. Manual references and existing previews retain their previous availability. [Platform coverage](extension-qualification.md#milestone-25-picker-coverage)

The host checks the selected URI's scheme, authority, and workspace folder. It generates a reference using `attachmentReference`, checks that it round-trips through `resolveWorkspacePath`, and validates the resource through the normal workspace boundary. Path segments are encoded once, with parent-directory segments kept literal. For example, a nested document can reference `../../media/caf%C3%A9%20%23%25%28final%29%252F.png`. The portable path rules exclude unsafe segments and references longer than 4,096 characters.

The picker checks regular-file metadata, refuses symlinks and junctions along the resource path, and checks the canonical selected path against the resolver target and root before reading. It reads at most 5 MiB plus one byte to detect growth, checks the raster signature, and passes the selected bytes to the webview for decoding under its existing CSP. Chromium's decoder handles pixels and animation frames. The 5 MiB limit caps encoded file bytes. A corrupt file, SVG, or a file above 5 MiB is rejected. Folio repeats validation at Insert and compares the canonical path, handle identity, size, timestamps, and SHA-256 of the bytes with the first observation. Editing the URL field turns the value into a manual reference.

The host binds each selection to one webview connection and Markdown revision. The dialog also checks the initiating editor document, mode, and selection. Milestone 2.6 keeps the displayed selection available while the webview attempts to decode a replacement. A cancelled chooser or failed decode preserves the displayed URL and alt text, and Insert still revalidates the selected asset. The host retains at most the displayed selection and one replacement candidate for that connection. Source inserts an escaped Markdown image with a CodeMirror transaction. Visual uses a ProseMirror transaction and the shared Markdown serializer. Native Save and Undo/Redo work through the revision-aware edit path and both Markdown recovery channels. Picker selections live in memory for the current connection. A stale or cancelled selection never applies on restart.

The picker uses metadata and read operations only. Folio performs no asset creation, copying, overwrites, moves, renames, deletes, or asset-side journaling. Filesystem validation observes a mutable path and a file handle at particular times. Windows Node and VS Code APIs provide no atomic guarantee covering the complete ancestor chain. A file can change before the first read or after the final confirmation, and a later preview resolves the reference again. A valid Markdown reference can subsequently break or resolve to different image bytes. The picker neither reserves a path nor promises immutable file identity. Automatic attachment uploads remain disabled everywhere.

## Deferred upload design

Milestone 2.7 reran the Windows desktop picker and strict filesystem checks. The supported browse environment is a trusted local Windows workspace on a fixed NTFS volume with a drive-letter file URI and empty authority. The native probe again admitted normalization-equivalent names, so the reference-only design and disabled automatic uploads apply to every backend. [Windows evidence](extension-qualification.md#milestone-27-environment-matrix)

The following sections retain the design and test requirements for a future qualified automatic-write backend.

### Selection and destination

1. Add an **Image from file** action in the VS Code editor. Use a webview file input for the desktop user's local file, including when the workspace extension host runs on another machine. Read one file, cap it at 5 MiB before allocating or transferring it, and send bounded bytes plus the display filename through the existing connection envelope. A browser MIME type is an early filter. The host validates the byte count, extension, and raster signature using the same formats as workspace preview. Reuse the existing image dialog for alt text and insertion. Start with this picker flow before considering drag and drop or paste. [VS Code Remote webviews](https://code.visualstudio.com/api/advanced-topics/remote-extensions#using-the-webview-api)
2. The host derives the document and workspace folder from the active custom editor session. Require a saved file in a writable, supported workspace folder. A called operation is bound to that document URI, containing folder URI, and connection. Offer the document-relative `assets/` directory by default. An optional resource-scoped `folio.attachments.directory` setting can specify a path relative to the containing workspace folder. Preview the target before writing. Validate settings from the workspace using the same rules as user-supplied paths, and check provider writability again when starting a write. A provider-wide writable result can coexist with read-only directories or a read-only Markdown document. Handle per-file metadata and actual write or permission errors. [VS Code FileSystem API](https://code.visualstudio.com/api/references/vscode-api#FileSystem)
3. Sanitize the basename for portability across Windows, macOS, and Linux. Strip path components, normalize Unicode to NFC, remove controls and Windows-reserved characters, and trim trailing dots and spaces. Use `image` for an empty stem or a Windows device name. Limit the stem to 100 UTF-8 bytes on a code point boundary and derive the lowercase extension from the validated format. Keep the original display stem for alt text. On collision, try `name-2.ext` through `name-100.ext`. Use a no-overwrite filesystem operation for the final name even when a preceding stat found it free. Treat canonically equivalent or case-folded existing filenames in that directory as collisions for checkout portability.
4. Calculate the link from the document's parent URI to the finalized asset URI using POSIX URI path segments. Verify that both URIs are in the same workspace folder, scheme, and authority. Percent-encode each filename segment once, including spaces, `#`, `%`, and parentheses. Keep `/` between segments and emit `./assets/name.png` or bounded `../` steps. Test the emitted reference through the existing resolver before returning it to the webview. Save only the relative reference in Markdown.

### Filesystem boundary

Put validation and publication in a host service next to `extension/src/resources.ts`. Share the raster signature checks and lexical containment rules with resource reads where their semantics match. Use URI segments, `Uri.joinPath`, and `workspace.fs` for provider-backed resources. Disallow absolute and parent segments in the configured asset directory. Walk from the selected root and reject symlinks, non-directories, encoded separators, controls, device names, and root or authority changes. Recheck the nearest existing parent before directory creation, then verify every component. For a `file` URI available to the extension host, also check canonical containment and use an exclusive, no-follow stage creation primitive where available. Revalidate before publication and after reading the final bytes. [VS Code virtual workspace guidance](https://code.visualstudio.com/api/extension-guides/virtual-workspaces)

Before enabling a provider for insertion, establish that it reports link metadata accurately and supports an exclusive staging create plus a same-directory no-overwrite publication under concurrent writes. For a provider that cannot satisfy these requirements, surface an unsupported destination before creating files. Document the guarantee for each supported provider.

### Milestone 2.3 qualification decision

| Destination or API | Established behavior | Insertion readiness |
| --- | --- | --- |
| Host-local Node `fs` on the tested Windows NTFS volume | `wx` allows one staging creator. Linking a complete stage to an unused name in the same directory allows one publication. The losing stage stays intact and can use a numbered suffix. Unlinking the successful stage leaves the published bytes intact. A junction substituted after `realpath` can redirect even a `wx` create. | Candidate for the first implementation milestone. Gate availability on a qualified filesystem and safe parent containment through create, publish, and cleanup. `fs.rename` can replace an existing name. A hard-link failure must leave the operation pending or unsupported, with no overwrite fallback. [Node filesystem API](https://nodejs.org/docs/latest-v24.x/api/fs.html) |
| Public `vscode.workspace.fs` | `writeFile` replaces bytes and exposes no exclusive-create flag. `rename` accepts `overwrite: false`, with execution delegated to the relevant provider. Public APIs expose neither an anchored path traversal primitive nor an identity-checked unlink. `isWritableFileSystem` reports scheme capability. | Generic provider writes are unsupported. A prior `stat`, a randomized stage name, or a post-write check cannot substitute for exclusivity or containment. [VS Code FileSystem API](https://code.visualstudio.com/api/references/vscode-api#FileSystem) |
| `WorkspaceEdit.createFile` with content | On tested VS Code 1.147.0, it rejects an already-existing entry, then delegates actual creation through a workbench write that can overwrite a competitor arriving after validation. The synthetic probe observed `{ create: true, overwrite: true }` and the competitor was replaced. The pinned workbench code registers file Undo with a delete operation against the staging URI. | Unsuitable for staging. An unrelated staging file operation could outlive promotion in Undo history. [Pinned file service](https://github.com/microsoft/vscode/blob/8a14f0cc1b08d531eb83255ea3764ae22aa932b5/src/vs/platform/files/common/fileService.ts#L329-L345) [Pinned bulk file edits](https://github.com/microsoft/vscode/blob/8a14f0cc1b08d531eb83255ea3764ae22aa932b5/src/vs/workbench/contrib/bulkEdit/browser/bulkFileEdits.ts) |
| Synthetic `folio-test-remote` | The test provider serializes its own map mutations. Two `rename` calls for one final name leave the winner and the losing stage. Injected failures leave partial stage bytes or complete published bytes even when a caller sees `Unavailable`. | Suitable for repeatable fault injection only. It establishes neither production provider guarantees nor real connection behavior. |
| Real Remote and other filesystems | WSL, Dev Containers, and SSH were unavailable. A Remote workspace host is expected to run where the workspace is hosted, so its native paths may refer to the server. URI scheme, authority, host placement, filesystem type, and operation semantics require separate evidence. Native macOS and Linux and other Windows volumes also remain unqualified. | Unsupported for insertion until qualified on the actual host and volume. A `file` URI, a successful preview, or a writable provider are insufficient. [VS Code Remote extension guidance](https://code.visualstudio.com/api/advanced-topics/remote-extensions) |

Use a trusted, saved, writable document in the containing workspace folder. Validate the proposed directory as portable relative components before filesystem access, including sibling roots, encoded separators, parent traversal, reserved device names, and reparse points. Compare URI schemes and authorities as well as complete path segments. Recheck canonical containment, but treat checks followed by path-based operations as race-prone. Before enabling a backend, demonstrate an anchored operation or an independently enforced destination boundary under a parent-swap test. Cleanup has the same constraint. A digest and file identity aid classification, but a subsequent path-based unlink can still target a replacement. Leave ambiguous or unprotected stages for review.

The final link operation protects the filesystem's own name equivalence. Folio must also check NFC and case-folded collisions for portability and serialize candidate selection among its own concurrent requests. Where the host filesystem permits equivalent spellings, a directory listing alone cannot prevent a non-cooperating writer from racing that check. Keep the initial supported scope narrow enough to meet the chosen collision contract and record it in qualification tests.

Keep the webview picker on the client and validate the declared and decoded byte counts on the host. The ceiling is exactly 5,242,880 bytes. Derive a canonical lowercase extension from the allowed raster format. A recognized header identifies the format. Decoder validity and truncation require additional checks. Reject mismatched extensions and signatures, SVG, and empty inputs. Keep the display name for alt text. Encode the final URI path segments exactly once, including parentheses, and run the generated reference through `resolveWorkspacePath`.

Existing image references continue through the current document parser, serializer, and preview service. An ordinary edit leaves authored relative paths, reference syntax, and image metadata intact. Folio sends validated preview bytes into the existing CSP and keeps workspace directories out of `localResourceRoots`.

### Milestone 2.4 qualification result

**Automatic attachment writes remain incomplete.** The preparation commit hid the unimplemented **Image from file** action and input in VS Code. The continuation fixed the shared reference dialog in the VS Code sandbox. The extension has no upload protocol, write service, destination setting, or asset-operation journal.

- `src/host/vscode/attachmentPath.ts` contains filesystem-independent preparation. It validates literal workspace-relative directory settings, produces NFC filenames with a bounded UTF-8 stem and lowercase raster extension, chooses numbered candidates from a listing, and emits same-scheme, same-authority, same-root relative references that round-trip through `resolveWorkspacePath`. It compares names using NFC and JavaScript case mappings. The helpers neither authorize paths on disk nor reserve candidates. The extension does not call them while uploads are disabled.
- `src/host/vscode/attachmentFilesystem.test.ts` exercises real files. Replacing the checked parent with a junction redirects exclusive staging and path-based hard-link publication. Replacing a staged entry after checking identity can make path-based unlink remove the replacement. The NTFS probe also publishes successfully beside a canonically equivalent name introduced after the listing.
- `tests/vscode/attachment-ntfs.ps1` probes user-mode `NtCreateFile` with a directory handle and a single relative leaf opened without following its reparse point. It detects a junction, blocks ordinary renames of both held fixture directories, writes and verifies an exclusive stage, and uses `NtSetInformationFile(FileLinkInformation)` with replacement disabled and a destination handle. The probe verifies matching stage and final file IDs, preserves existing bytes at exact and case-equivalent names, and removes the stage by its live handle while preserving the published bytes. Anchored publication still permits NFC and NFD spellings to coexist. During investigation, denying write sharing on the destination handle made the native link call return `STATUS_SHARING_VIOLATION`. The successful probe allows write sharing and denies delete sharing. The fixture opens its workspace by absolute path. Full ancestor pinning, in-place reparse changes, and cleanup after losing a handle remain unqualified. [NtCreateFile](https://learn.microsoft.com/windows/win32/api/winternl/nf-winternl-ntcreatefile) [FileLinkInformation](https://learn.microsoft.com/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_link_information) [SetFileInformationByHandle](https://learn.microsoft.com/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle)

The continuation reran all six NTFS filesystem cases under strict qualification and the native handle probe. The results support keeping automatic writes disabled on local NTFS and all other volumes and providers. The [platform runbook](extension-qualification.md#milestone-24-local-filesystem-probes) reproduces the Windows evidence.

### Planned publication and recovery

1. Wait for the active view's existing edits to settle, then capture the insertion position and committed revision. If the selection or committed revision changes while the request runs, ask for a new insertion position before changing Markdown. Bind prepare, publish, and status to the initiating connection, document, and workspace. Key prepare by a stable client request ID within that connection so a retry returns the same host-issued operation ID. Serialize state changes by operation ID and reject attempts to change the payload or destination of an existing operation. Keep the operation record in VS Code workspace storage separately from the Markdown draft journals.
2. Before filesystem changes, persist the operation ID, document and root URIs, staging URI, candidate final URI, byte length, digest, and stage. Use a uniquely named staging file in the destination directory. Persist a new intended final URI before each collision retry. Verify the staged bytes, record the backend's available stage identity evidence, and publish under the chosen name with overwrite disabled. Verify that the final entry is a regular file with the expected digest and the identity that the publication operation established against the stage. Record publication before returning the relative reference. A lost reply requires checking both paths after the connection returns. If the backend cannot establish ownership after a restart, including when identity may have been reused, classify the result as ambiguous.
3. Insert the link through the existing shared edit path. The editor journal and host backup immediately checkpoint the new draft. The normal native acknowledgement still verifies the exact proposal against `TextDocument`. Save, Undo, and Redo follow VS Code's Markdown history. The binary asset may be shared or become referenced later, so Undo removes the Markdown reference and leaves the file. A status record can report a published asset independently of whether the link was acknowledged.
4. On interruption, inspect the operation record and revalidate workspace identity before reading either path. If neither file exists, prompt for reselection when the originating bytes are gone. If an owned stage still exists, verify it before offering retry or cleanup. A finalized file with matching bytes and verified publication identity can supply its relative path for explicit insertion or copy. Identical bytes alone leave ownership ambiguous. Recovery never inserts text automatically after a restart. A rename, deletion, changed root, or conflict requires a fresh insertion decision. Only remove a staging file through a backend that preserves its ownership check through deletion. Never automatically remove a published or ambiguous file. Markdown recovery remains available independent of the operation record.
