## Architecture

Format adapters use format-specific state. A common Markdown intermediate would lose information about Word structures, PDF pages and workbook cells. Independent editors with separate storage and file flows would duplicate recovery, import decisions and export checks. The design shares the document lifecycle and reuses the appropriate editing components while letting each adapter define fidelity.

| Boundary | Proposed responsibility |
| --- | --- |
| Format selection | Use a small registry under `src/document/formats/`. Route by case-insensitive extension and validate the selected content before creating a draft. Treat MIME as a hint. For DOCX, verify package content types, relationships and the Word main part. A ZIP signature alone cannot distinguish DOCX from XLSX. [ECMA-376 Office Open XML](https://ecma-international.org/publications-and-standards/standards/ecma-376/) |
| Adapter contract | An adapter exposes its format ID, supported import/export targets and editing capabilities. Import returns a typed payload and structured issues, or a rejection. Export takes a snapshot and explicit options, derives losses for that snapshot and produces validated bytes, a filename and a media type. Both operations accept cancellation and enforce input and output budgets. The host owns file selection and delivery. |
| Document state | Share stable document ID, format, schema version, title and revision. Keep native payloads discriminated by format. Persist the original filename, immutable original bytes and content fingerprint for imported TXT and DOCX. Store immutable blobs once per document lineage and reference them from typed drafts and history snapshots. Commit records and blob links together. Reclaim an original only when explicit deletion leaves no retained draft or version referencing it. |
| Markdown | Retain `src/document/markdown.ts`, `src/document/files.ts`, `src/editor/useDocument.ts` and the current Markdown model. Authored Markdown remains authoritative for Visual, Source and Split. Preserve `folio.markdown`, native `TextDocument` Save and Undo/Redo, exact-text acknowledgement and both recovery channels. Keep Markdown-specific assets, diagrams and parser options on that path. |
| Other editors | TXT uses a plain CodeMirror configuration with Markdown language services and rich formatting disabled. DOCX uses a limited Tiptap/ProseMirror schema and structured import mapping. PDF uses a page surface and XLSX/CSV use a grid with workbook or table state. Share shell UI, find presentation and command plumbing where their semantics match. Gate actions on format, host and document capabilities so unsupported commands never reach the editor. |
| Persistence and search | Extend `src/document/workspace.ts`, `workspaceStorage.ts`, `versions.ts` and `src/host/contracts.ts` to store and restore typed drafts. Read existing untagged drafts and version content as Markdown, preserving content, encoding metadata and history. Scope search to the format's visible text, pages or cells and identify matches in that coordinate system. Apply replacements only through an editor with compatible editing and selection semantics. |
| Host and runtime | Keep `src/host/browser.ts` responsible for browser storage and delivery. Build DOCX processing as a lazy-loaded local worker with bounded input. Future binary providers own their canonical document in the extension host and expose validated, revision-tagged messages, with Save and backup independent of webview visibility. Local/private processing and the existing VS Code Trust and CSP restrictions remain requirements. |

Model import dispositions as editable, editable copy with issues, or rejected. Each issue should identify the affected feature, location when available, and whether it is preserved, approximated or omitted. Export recomputes issues for the requested target and current revision. A confirmation applies only to that target, option set and revision. Format adapters must distinguish an unsupported construct they can identify from content whose scope or effect they cannot safely determine. Reject the latter when its omission would make an editable view misleading.

Phase 7A implements editable and rejected import outcomes, structured diagnostics, and the TXT export outcome that requires a newline choice. `src/document/formats/content.ts` provides typed TXT, Markdown and DOCX state, with an untagged Markdown fallback for existing records. `src/document/formats/registry.ts` is the format and byte boundary. `src/document/workspaceStorage.ts` uses the existing v4 IndexedDB store for original bytes and SHA-256 metadata, while `src/document/versions.ts` retains typed content and the pre-restore draft. The DOCX record stores ProseMirror JSON as the canonical document and a derived text index for shared document actions. `src/editor/useDocument.ts` validates DOCX editing transactions against the bounded subset before accepting them. Markdown syntax services run only for Markdown. Existing VS Code native editing and recovery continue on the Markdown path.

## Phase 7 compatibility contract

### TXT

- Import and export UTF-8 with or without a BOM. Decode strictly and tell the user when an input is invalid UTF-8 or appears to be binary. UTF-16 and legacy encodings are deferred. TXT imports have a 16 MiB limit and edited exports a 32 MiB limit. Preserve literal text, whitespace, blank lines and final newline state. Markdown punctuation stays literal during editing and export.
- **Download original** returns the exact imported bytes. A no-edit TXT export also matches those bytes. For edited files with uniform LF, CRLF or CR, preserve the existing newline style and BOM. For an edited file with mixed endings, show a normalization notice and require the user to choose an output newline style before exporting a copy. A new file defaults to LF and UTF-8 without a BOM. Reject invalid output text before UTF-8 encoding can substitute characters. Reject leading literal `U+FEFF` for an edited BOM-less copy because reimport would interpret it as a BOM. The higher export limit lets larger edited drafts be downloaded even when the result exceeds the import budget.
- Provide plain-text editing, undo/redo, find/replace and typed draft and version recovery. Check edited text independently from the original-byte fingerprint so undo back to the imported content can restore the exact export behavior.

### DOCX

- Ordinary, unencrypted `.docx` files use supported main-body elements. The subset is paragraphs and empty paragraphs, heading levels 1–6, bold, italic, underline, explicit breaks, safe links, single-level bullet and decimal lists with one paragraph per item, and rectangular tables of paragraphs with an optional uniform first header row. Standalone displays a visual editor, with heading navigation, find/replace, local saving and history. It offers table row and column commands. Column resize waits for a width model and independently verified round trip. Generated files use Folio's styles and page defaults.
- Disclose reflow and changes to pagination, margins, fonts, advanced numbering, custom styles and layouts. Headers, footers, images, comments, tracked changes, footnotes, fields, math, charts, embedded objects, content controls, and complex or nested tables are outside the initial fidelity promise. Keep these in the original and report any approximation or omission in the editable copy. A document with unsupported features can enter the editable-copy flow only when the adapter can identify the limitations and extract supported content confidently. Reject unreadable, encrypted, protected, malformed, legacy `.doc`, macro-enabled and otherwise unsafe packages, as well as cases where the parser cannot determine the impact of omitted content.
- Keep the original available byte-for-byte. An edited DOCX export is a new `.docx` generated from the supported model. Show the expected losses before export and require confirmation for approximations or omissions. Hold the draft if output validation or delivery fails. Use a suggested copy filename and leave in-place binary saving outside Phase 7. Check semantic structure and independent-reader interoperability.
- The loss review lists detected features and locations and includes the generated copy's layout behavior. It binds to the captured document ID, revision, target and confirmation. The worker validates output by reading it back and comparing the supported structure before delivery. Cancellation, stale revisions and validation failures leave the draft and original intact.

### Phase 7B codec and limits

- The browser host loads the `workerClient.ts` worker only for DOCX. `src/document/formats/docx/readZip.ts` validates the ZIP directory, path names, flags, local records, supported compression, and CRCs. `readPackage.ts` validates OPC content types and relationship sources and identifies the main Word part. `read.ts` maps supported WordprocessingML and reports unsupported or approximated constructs. `write.ts` emits Word parts, styles, numbering, and relationships. The worker enforces semantic reimport before delivery. Phase 7B shipped this codec in the standalone host. Phase 7C shares it with a separate VS Code host worker.
- Archive bounds are 24 MiB package size, 512 entries, 16 MiB per expanded entry, 64 MiB aggregate expansion, and 200:1 expansion above a 64 KiB floor. XML bounds are 8 MiB per parsed part, 64 levels, 240,000 elements, 64 attributes per element and 480,000 aggregate attributes per parsed part. The rich model accepts up to 100,000 nodes and 8,388,608 UTF-16 text units. The writer uses stored ZIP entries to stay inside the reader's expansion policy. The browser cancels by terminating the worker and applies a 25-second processing timeout.
- No package parts go to the filesystem. Internal relationships resolve within the package. External relationships are never fetched. Only explicitly opened HTTP, HTTPS, `mailto` and `tel` link destinations are supported, with unsafe or ambiguous URL text rejected. The parser prohibits DTDs and external entities. The importer refuses macros, protected and encrypted documents, ambiguous structures, and unsupported features whose effect on the visible body cannot be inferred safely.
- The pinned codec uses small ZIP and XML primitives rather than a general office engine. `fflate` provides bounded-stream DEFLATE and ZIP writing while Folio controls package validation. `saxes` provides strict namespace-aware XML in a browser worker and `xmlchars` supplies its character tables. JSZip adds general-purpose package features and dependencies that the scoped codec does not need. The `docx` npm package offers a broader document generator, while Folio requires a matching subset reader and explicit diagnostics. The chosen primitives let both directions share one bounded implementation. [Package and copying obligations](extension-distribution.md#standalone-docx-worker-dependencies) · [ECMA-376](https://ecma-international.org/publications-and-standards/standards/ecma-376/)

### Save, conflicts and recovery

- Clarify **Save draft**, **Download original**, and **Export copy** in the UI. Autosave and history update local drafts only. Phase 7 TXT and DOCX export uses a new file via a browser download. Report successful submission as a download request, since the browser controls final placement. A future host write must validate the payload before publication and prove safe destination replacement and conflict detection on each supported provider before enabling in-place save.
- Import failures, cancelled imports and blocked or exhausted storage must leave the active document intact. Commit a new summary and typed draft with its original bytes before opening the tab as saved. Bind exports to captured revisions. If the document changes during preparation, stop and ask for a new export from the current revision. Quota failure, worker cancellation and stale writes keep the current editable draft available, with a visible recovery status and explicit retry or export options. Never mark a failed checkpoint as saved.
- Reuse the current expected-state checks for multiple standalone tabs. Version restore retains the current conflicting draft and the selected historical revision for review. Keep the DOCX original and import issues with every relevant version so a restored draft can still explain what export will omit. Recovery requires explicit selection and must never silently replace an original or another tab's newer draft.

## Phase 7 sequence and acceptance

Phase 7A completed steps 1 and 2. Phase 7B covers steps 3 and 4 for the documented standalone subset. Step 5 applies to each milestone. Read the handoff for actual tool and independent reader results. 1. **Define the format and persistence boundaries.** Add the discriminated payload, adapter registry and typed issue definitions in `src/document/formats/`. Wire routing through the standalone file picker and drag/drop in `src/App.tsx` via browser host file operations. Keep the existing Markdown adapter calling the current codec and editing path. Add tagged drafts/version reads and writes, with untagged records interpreted as Markdown. Prove that a pre-Phase 7 IndexedDB fixture opens and restores history with exact Markdown source, BOM and newlines. Exercise a blocked storage upgrade and competing writes before enabling a new format.
2. **Deliver the TXT workflow end to end.** Implement the TXT adapter under `src/document/formats/`, add the plain CodeMirror surface under `src/editor/`, and wire the existing draft, history, search and export UI using format capabilities. Fixture tests compare untouched and edited bytes for UTF-8 and BOM, LF/CRLF/CR, mixed endings, empty documents, trailing whitespace and final newlines. Check literal Markdown syntax, multibyte text and rejection of malformed or binary input. A browser flow must import, edit, reload, restore a version and export without changing the input file.
3. **Qualify a DOCX codec and import the supported subset.** Evaluate candidate package readers and writers with pinned versions, licenses and transitive notices, browser-worker fit, package relationship handling, fidelity, cancellation and memory limits. Select a dependency only after the fixtures prove it suitable. Add import mapping and the restricted Tiptap surface. Compare mapped structure and location-specific issue reports for supported, partially supported, malformed and over-budget fixture files. Accept a correctly structured DOCX with missing MIME and reject an XLSX renamed to `.docx`. Test that failure or cancellation creates no draft, and that editable copies can always recover the original bytes.
4. **Complete DOCX export and recovery.** Generate and validate a new DOCX for an immutable snapshot, bind the loss review to its revision and check that a stale confirmation cannot publish another revision. Verify paragraphs, headings, marks, links, lists and simple tables after reimport and in Word and LibreOffice. A browser flow must edit, close or reload, restore a version, reopen the original or export a copy. Inject quota exhaustion, cancellation, writer failure and concurrent tab changes and verify consistent draft status, unchanged originals and recoverable content.
5. **Qualify the integrated feature before closing Phase 7.** Run focused Vitest tests with `npm test -- <affected-test-files>`, Chromium file workflow cases with `npm run test:e2e -- <affected-specs>`, and `npm run build` and `npm run build:extension` when application changes land. Run targeted VS Code desktop Markdown cases for native default, exact text/bytes, Save, Undo/Redo, and recovery when shared code changes. Record tested browsers, supported formats and known fidelity gaps in the handoff. Verify that neither new format makes the Markdown startup load binary codecs or changes its commands, storage, rendering or sync paths.

## Phase 7C native document integration

- TXT uses the Markdown-derived revision and recovery bridge over a native `TextDocument`, with literal CodeMirror and strict UTF-8 input checks reused from Phase 7A. Local files with uniform LF or CRLF and optional BOM support native saves. Folio uses a read-only preview for endings and encodings the native buffer cannot faithfully represent.
- DOCX uses a native `CustomDocument` with Phase 7B's canonical model, original bytes, SHA-256, and import diagnostics. Format-tagged messages carry bounded edits against the current revision. The extension host validates the proposed tree and journals it before emitting a native history event. ZIP and XML processing run on open, revert, and reviewed copy export in a separately bundled worker. A native backup stores the package and the editable revision. If its revision lags an acknowledged journal, both remain available.
- Workspace DOCX writes require a file operation that can enforce the expected destination identity through publication. Neither a preliminary fingerprint nor an overwrite option provides that operation on the generic API. Phase 7C delivers reviewed copy export with no workspace mutation and keeps the write gate open. [Host details](extension-readiness.md#phase-7c-text-and-binary-editors) · [Qualification](extension-qualification.md#phase-7c-multi-format-qualification)
- Starting in Phase 8, implement the extension integration in the format's own phase. Phase 8 delivered PDF as a read-only custom editor with no workspace writes, plus new-file-only PDF copies. XLSX will need sheet-aware binary history and its own package and save qualification.

## Phase 8 PDF boundary

- Open PDFs in a read-only page viewer with page navigation, zoom and page rendering. Offer search, selection and copy where usable embedded text is available. Image-only pages can be viewed. OCR, PDF content editing, annotation or form authoring, redaction, signatures and encrypted files are deferred. Render locally with cancellation and bounded page work. Embedded scripts, forms and external actions are inert.
- Export eligible Markdown, TXT and DOCX drafts to newly generated PDFs using a paginated rendering path. Preview page breaks and disclose unsupported content or rendering changes. An opened PDF stays a page-oriented document, with an exact-original download available. PDF-to-editable-text conversion and saving changes back into imported PDFs are deferred.
- Keep page numbers and optional text positions in the PDF model. The common lifecycle needs read-only capabilities, cancellable page work and lazy viewport rendering without requiring every adapter to expose `source` or a rich-text tree.

### Phase 8 implementation

- `PdfContent` is a fourth discriminated payload. It carries page count, detected features and the immutable original reference, and its `source` is always empty. `formatCapabilities` reports `readOnly`. The registry identifies `.pdf`, validates the bytes with the viewer engine before committing, and rejects PDF export of an imported PDF. `recordVersion` refuses PDF content, and the standalone lifecycle skips automatic versions for it.
- Text positions are not persisted. The viewer extracts a bounded per-page text index from the original and maps matches to pdf.js text-layer items. The shared `PdfViewer` serves standalone, the VS Code `CustomReadonlyEditorProvider` and the export preview.
- PDF export is a target of the existing revision-bound export pattern rather than a new adapter. Markdown, TXT and DOCX build a print model from their own representation (rendered ProseMirror tree, literal text, structured DOCX model), never through Markdown for other formats. Generation and validation are local and bounded. [Phase 8 architecture](phase-8-pdf.md)

## Phase 9 CSV and XLSX boundary

Phase 9 uses IronCalc and a sparse typed workbook in the shared lifecycle. The [Phase 9 record](phase-9-spreadsheets.md) supersedes the initial design below where it describes partial or changed behavior, including explicit local calculation.

- **CSV** · Import, edit and export a single table of text cells. Carry encoding and dialect, including delimiter, quoting, embedded newlines, line endings and optional header interpretation. Preview and let users correct ambiguous dialect choices. Preserve leading zeros, literal formula-like strings and empty fields. Flag formula-like cells at export and require an explicit choice between unchanged data and a spreadsheet-safe copy that changes the affected values. CSV export from a workbook requires an explicit sheet selection and disclosure of features the text format drops.
- **XLSX** · Open supported workbooks with multiple sheets. Preserve sheet identity, names and order, typed cell values and supported number and date formats, including the workbook's date system. Edit ordinary cells and export a new workbook. For the initial subset, preserve supported formula text and its cached result when unchanged, and never execute imported formulas. If an edit invalidates a cache, expose it as stale or omit it from the exported copy. Block editing/export cases where formulas or dependent workbook features cannot be carried safely, with a read-only view when reliable. Charts, pivot tables, scripts, macros, external links, encrypted workbooks and full Excel calculation fidelity are deferred. Preserve original bytes and disclose unsupported workbook content before offering any reduced copy.
- Keep workbook revision state, worksheet IDs, cell coordinates, cell type and formula text in the format model. Share file routing, diagnostics, blob persistence and export review with DOCX. Share bounded package I/O only where the Word and workbook rules actually match.

## Release gate

The first public release must include the scoped Markdown, TXT, DOCX, PDF and XLSX workflows and the implemented and tested editing capabilities tracked in the matrix. Qualify and document what each public channel supports, including hosts, open/import options, editing modes, export targets, unsupported features and recovery limits. Withhold public GitHub and Marketplace publication until this gate is met, the final artifact and source review is complete, and publication is explicitly authorized. The existing ELK/MELK source and notice work remains a distribution requirement. Review any newly introduced format libraries as part of the exact release artifacts.
