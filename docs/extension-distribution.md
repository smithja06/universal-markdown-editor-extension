# Folio VSIX distribution record

## Phase 9 spreadsheet runtime

Phase 9 pins the IronCalc bindings at 0.9.1 and bundles the XLSX binding under the MIT option. The native codec runs separately and loads the bundled spreadsheet.wasm. The webview uses a lazy inline worker with the same WASM bytes. The published npm package carries notices generated from the Rust lockfile and the Unicode license for its CLDR data. Folio ships these alongside the MIT notice in the standalone build and the VSIX. [Spreadsheet notices](../public/SPREADSHEET_THIRD_PARTY_NOTICES.txt) · [Phase 9 architecture](phase-9-spreadsheets.md)

The final Windows test VSIX contains 204 entries and is 8,270,611 bytes. SHA-256 is 9ca957adaf31873b62b01f532524ef0e8c8cf5c3c22c0734168e1e49aabd9241. Inventory checked archive CRCs, the manifest and files allowlist, every built webview file, and byte equality for the standalone notice and packed npm WASM. The packaged WASM is 2,546,925 bytes with SHA-256 03235ab1bccd87d0847dceba2c9defdd4f4ba9f47f9ddf098e53a423b3cc196c. The spreadsheet notice is 178,868 bytes. A Chromium production network probe saw zero XLSX worker requests on Markdown startup and zero out-of-origin requests while explicitly exercising local spreadsheet calculation.

## Phase 7C extension DOCX worker

The VSIX includes `dist/docx-codec.cjs`, a separate Node worker built from `extension/src/docx-codec.ts` and the same codec entry used by the standalone worker. The host resolves it from its own installed directory when DOCX open, revert, or reviewed-copy generation requires the codec. Markdown and TXT load the existing webview and no DOCX ZIP or XML engine. The standalone browser worker remains separate.

The VSIX allowlist includes `dist/DOCX_THIRD_PARTY_NOTICES.txt`. The extension build copies the same pinned `fflate`, `saxes` and `xmlchars` notices distributed by standalone Folio. No new dependency versions or licenses were introduced. Packaging checks compare the notices and worker in the archive against the build, and the installed smoke opens and exports DOCX from the actual VSIX. ## Requirements and release decision

- EPL 2.0 §§1 and 3 require the preferred form for modification of the distributed Program, including applicable source, documentation source, and configuration. The binary must explain that source is available under the EPL and how to get it by a customary means. Preserve attribution, license and other notices, and evaluate the object-code distribution terms under §3.1(b), including downstream distribution. Select EPL 2.0 for elkjs and ELK. Their conditional GPL option is separate. Ask legal review to confirm how the final combined chunk and its minification affect notice preservation and the scope of any Modified Works. [EPL 2.0 §§1 and 3](https://www.eclipse.org/legal/epl/epl-v20.html)
- EPL 1.0 §3 separately governs EMF GWT. Under separate object-code terms the agreement must direct recipients to source available from the distributor through a reasonable means, preserve copyrights, and carry the required protections for upstream contributors. The VSIX includes the full EPL 1.0 text and exact upstream source JAR links. Host the verified source under the applicable license alongside the release so recipients can obtain it from Folio. Review the chosen binary terms and release-channel terms for both EPL versions. [EPL 1.0 §3](https://www.eclipse.org/legal/epl-v10.html) · [Packaged EPL 1.0 text](https://github.com/spdx/license-list-data/blob/main/text/EPL-1.0.txt)
- Preserve bundled MIT, ISC, BSD, Apache 2.0, and OFL copyright, license, and disclaimer text. Apache 2.0 §4 also requires reviewing upstream NOTICE content and marking altered files where applicable. Preserve OFL for the distributed font files, including the font notices. Verify the GWT class and data closure against the emitted worker for additional runtime notices or licenses, including any emulation and locale data, and preserve the original emitted-input headers as appropriate. [Apache 2.0 §4](https://www.apache.org/licenses/LICENSE-2.0) · [SIL OFL 1.1](https://openfontlicense.org/open-font-license-official-text/)

**External distribution is blocked pending source and terms review.** The VSIX contains the exact upstream source acquisition links and additional notices. The pinned build recipe also references Xtend 2.36.0 support, GWT tooling, and the mutable `org.eclipse.elk.core.meta:0.13.0-SNAPSHOT` MELK generator. The current Maven snapshot metadata postdates the elkjs release. The final chunk has Xbase symbols and no `org.eclipse.xtend` package marker. It also has GWT `DateTimeFormatInfoImpl` markers, whose source identifies Unicode CLDR data. A source-file or compiler mapping is needed to distinguish build-only dependencies and shaded or optimized runtime code and data. The Xbase and Xtend source JARs are retrievable. The exact MELK snapshot and complete runtime notice set are open. [MELK snapshot metadata](https://central.sonatype.com/repository/maven-snapshots/org/eclipse/elk/org.eclipse.elk.core.meta/0.13.0-SNAPSHOT/maven-metadata.xml)

## Rechecking an artifact

Run `npm ls elkjs dompurify pdfjs-dist pdfmake dejavu-fonts-ttf --omit=dev`, inspect the generated Vite notices and `dist/PDF_THIRD_PARTY_NOTICES.txt`, and open the VSIX as ZIP. Check every entry against the manifest allowlist and expected VSCE metadata, compare webview assets byte-for-byte with `extension/dist/webview`, and check referenced HTML entries. Reject dev or unexpected files, source maps, packaged dependency trees, or credentials. Confirm the host input list with `npx esbuild extension/src/extension.ts --bundle --platform=node --target=node20 --external:vscode --outfile=test-results/audit-host.cjs --metafile=test-results/host-metafile.json`. Compare the output against the VSIX host bundle. Inspect `node_modules/mermaid/dist/chunks/mermaid.core` and its source maps for prebundled code, and check the packaged ELK chunk for upstream package markers. Reinspect the source links, notices, and final VSIX checksum whenever the lockfile or packaging changes.
